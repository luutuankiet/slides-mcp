# v2.1.0 — Curated write wedge for agent legwork

A targeted softening of v2.0.0's "no write surface" stance. v2.1 brings back two tools for legwork-shaped edits, with a multi-granularity post-state return that's first-of-its-kind in MCP server design.

This is **not** a return to v0.x ambitions. The v0.x → v0.11 write surface (archetypes, briefs, restyle, plan_deck, theme_swap, exec_batch_update) tried to make the agent a first-class creative author of decks. That investment is sunk cost — pixel-perfect creative authoring via Slides API on brownfield decks is a losing game. v2.0.0's read-only refactor was the right cut.

What we missed: there's a different shape of work where v2.0.0's all-or-nothing read-only stance over-corrected. **Legwork** — repetitive bulk edits humans hate doing manually but where 1 cm of layout slop is fine. Section footers showing "Section 2/4 · prev: Discovery · next: Build". Global font swaps. Bulk find-and-replace across a deck. Timestamps on every slide.

For these tasks, the agent doing the legwork while the human reviews + fine-tunes is genuinely useful. v2.1 ships that wedge.

## What's in

Two tools.

### `exec_batch_update(deck_url, requests, dry_run?, confirm_destructive?, post_state?)`

Raw passthrough to Google Slides `batchUpdate`. The agent composes Request dicts directly from the [Slides API Request reference](https://developers.google.com/slides/api/reference/rest/v1/presentations/request); the server forwards verbatim. Mirrors the v0.1.1 escape hatch (LOG-006 in the dev journal), upgraded with the v2.1 differentiator below.

- `dry_run=True` → returns `{request_kinds, preview, destructive_kinds_detected}` without firing
- `confirm_destructive=True` required for: `deleteObject`, `deleteSlide`, `deleteText`, `deleteTableRow`, `deleteTableColumn`, `deleteParagraphBullets`, `replaceAllText`, `replaceAllShapesWithImage`, `replaceAllShapesWithSheetsChart`
- `post_state` ∈ `{"full", "summary", "outline", "none"}` (default `"summary"`)

### `add_section_footers(deck_url, sections, template?, footer_position?, overwrite_existing?, confirm_destructive?, post_state?)`

The proof tool: turns a section map into a footer on every slide.

```python
add_section_footers(
    deck_url=...,
    sections=[
        {"name": "Discovery", "slide_range": "3-7"},
        {"name": "Build",     "slide_range": "8-15"},
        {"name": "Validate",  "slide_range": "16-22"},
    ],
    template="{section_name} · {position}/{total} · prev: {prev_name} · next: {next_name}",
    footer_position="bottom-right",
)
```

Uses deterministic objectIds (`slides_mcp_footer_<sid_suffix>`) so re-runs are idempotent. `overwrite_existing=True` (default) deletes prior footers before recreating; the destructive guard kicks in when there are any prior footers, requiring `confirm_destructive=True`.

## Why "verify-after-write multi-granularity return" matters

Both tools share a return shape that's the v2.1 design differentiator:

```python
{
    "applied_request_count": 5,
    "request_kinds": [...],
    "replies": [...],
    "warnings": [...],
    "affected_slide_ids": ["g1", "g2", "g3"],
    "post_state": {
        "deck_outline": {...},   # always (unless post_state="none")
        "slides": [...]          # only when post_state in ("summary", "full")
    },
    "isError": false
}
```

The `post_state` envelope cuts the fire-then-read round-trip the agent would otherwise need to verify what changed.

We did look first. Three-fork research surveyed Anthropic's `code_execution` tool docs, the MCP June 2025 spec, AWS Labs MCP DESIGN_GUIDELINES, and three production MCP servers (`matteoantoci/google-slides-mcp` 177★ — exact analog; `modelcontextprotocol/servers/git`; `makenotion/notion-mcp-server`). Findings:

- Anthropic's `code_execution` returns `{stdout, stderr, return_code}` — no side-effect surface
- MCP June 2025 spec defines `structuredContent` channel for machine-readable returns, but doesn't prescribe what goes there for write tools
- `matteoantoci/google-slides-mcp` returns Google's raw `BatchUpdatePresentationResponse` only — agent has to call `get_presentation` again
- `mcp/git` returns terse imperative strings ("Changes committed successfully with hash X")
- `notion-mcp-server` inherits whatever the upstream REST returns (Notion's REST is generous; Slides API is not)
- AWS Labs guidelines and r/webdev consensus: REST-PUT-returns-resource. But **multi-granularity** (per-mutated-entity AND aggregate-context) is not formalized anywhere.

slides-mcp v2.1 names the pattern explicitly: **verify-after-write multi-granularity return**. The agent gets back both the touched slides (per-entity) AND the deck outline (aggregate) in the same response.

## What's still out

Everything from v0.x that overreached:

- archetype builders, theme briefs, brand assets, plan_deck, theme_swap
- preview primitives (PIL swatches, contact sheets, archetype previews)
- catalog tooling
- audit tooling (color drift, font drift, brief coherence)
- variant generation
- icons, install_skill CLI, skill bundle

These don't come back. The wedge is `exec_batch_update` + `add_section_footers` + the cookbook. New convenience tools accumulate from real usage, not scaffolding.

## OAuth scope migration

v2.0.0 narrowed the OAuth scope to `presentations.readonly`. v2.1.0 keeps that as the default for fresh consents — most users want to read first. To use write tools:

- **Existing v0.x tokens** (broader `presentations` scope from before the v2 cut): keep working untouched. v2.1 honors the granted scopes per the v2.0.1 OAuth fix (LOG-032).
- **Fresh v2.x tokens**: re-run `slides-mcp-auth` with an OAuth client configured for the `presentations` scope (not `presentations.readonly`). The server surfaces a 403 with an actionable error pointing at the re-consent flow.

We deliberately did not auto-upgrade the default scope. Capability ≠ usage; if you don't need writes, the read-only token is a smaller security surface.

## Layout caveat (NON-NEGOTIABLE)

v2.1 explicitly accepts that pixel-perfect layout is impossible without visual feedback loops. The agent works blind on geometry — `add_section_footers` places the footer at approximate coordinates, not pixel-perfect. If precise placement matters, the human should fine-tune in the Slides UI after the agent does the bulk work.

## Migration

If you're on v2.0.x with the read-only stance and don't want writes — nothing to do. The new tools sit alongside; you don't have to call them.

If you want the write surface — re-run `slides-mcp-auth` (see OAuth migration above) and start with `dry_run=True` on `exec_batch_update` to confirm plumbing.

If you depended on v0.x write tools — pin `uvx slides-mcp@0.11.0` (v0.11 is preserved at that tag with the full v0.11 surface).
