# v2.0.0 — Read-only refactor

**The pivot.** v0.x → v0.11 chased a sophisticated write surface for Google Slides: archetypes, briefs, restyle, plan_deck, theme_swap, exec_batch_update. After many sessions debugging Google Slides API edge cases on real brownfield decks (autofit regressions, color drift, archetype mismatches, opaque rejects), the conclusion landed: **brownfield slide editing via the Slides API is a losing game.** The investment is sunk cost.

v2 is a complete overhaul with a different vision: **be a great reader of slides, period.** The use case is conversation — paste a deck URL, talk about it.

## What's in

5 tools, read-only, token-efficient:

| Tool | Purpose |
|------|---------|
| `auth_status()` | Token health |
| `get_deck_outline(url)` | ~20 tok/slide whole-deck index — first call on any new deck |
| `read_slides(url, slides?, detail?, include_notes?, include_images?)` | Primary read primitive — outline / summary / full / raw |
| `search_deck(url, query, slides?, regex?, ...)` | Substring or regex search across title/body/notes |
| `render_thumbnail(url, slide_id, size?)` | Single PNG when visual layout matters |

### Detail modes

`read_slides` mirrors `read_files`: one tool, multi-mode, batched. Pick the cheapest detail that answers your question.

- `outline` (~20 tok) — title + archetype + element_count + has_notes/has_image flags
- `summary` (~80 tok) — title + joined body preview + image_count + notes preview
- `full` (~150 tok) — title + every body string + image refs + tables/charts + full notes
- `raw` (~400 tok) — every shape with geometry + style + runs (debug; faithful)

### Slide selectors

Same flexibility as `read_files`'s per-file spec:

```
slides=None              # all slides
slides="slide_id"        # one slide
slides="3-7"             # 1-indexed inclusive range
slides=["id1","id2"]     # explicit list of object_ids
slides=[1,3,5]           # 1-indexed positions
slides={"first":5}       # head
slides={"last":3}        # tail
slides={"with_notes":true}
slides={"with_image":true}
```

**48 tools → 5 tools. ~5000 lines of write-side code deleted.**

### Module deletions

`archetypes.py`, `archetypes/`, `audit.py`, `catalog.py`, `create.py`, `diff.py`, `icons/`, `install_skill.py`, `swatch.py`, `text_range.py`, `theme_brief.py`, `theme.py`, `themes/` — all gone.

### Test trim

497 tests → ~25 tests. 28 test files removed (write/brief/preview/icon/audit/diff/create suites). Kept `test_normalize`, `test_classify`, `test_slides_api_parsing`; rewrote `test_projection` for the four new modes (~25 cases).

### Skill removed

`skills/slides-mcp/` is **gone in v2** (initially trimmed to a 1-page SKILL.md, then dropped entirely on advisor review). Tool docstrings are the canonical agent reference: every tool in `server.py` carries a verbose docstring covering selectors, detail modes, and tradeoffs — FastMCP returns those to MCP clients on connect, so paying for a duplicate skill file would double-bill the same content. The unique "anti-patterns" content from the old skill was promoted into `README.md`.

Migration: nothing to do — the v0.x install CLI was already dropped, so most users never had the skill installed locally.

### Dependency trim

Dropped: `pillow` (PIL preview), `pyyaml` (no YAML emission), `pydantic` (never used directly). Dev: dropped `python-pptx`. Wheel `force-include` for embedded skill data also removed (no install command in v2).

## Migration

If you depended on v0.x write tools, pin: `uvx slides-mcp@0.11.0`. The full v0.11 surface is preserved at that tag.

### OAuth scope tightening (breaking)

v2 narrows the OAuth scope set from `[presentations, drive.file]` (v0.x) to `[presentations.readonly]`. v0.x tokens with the broader grant continue to work (the API call layer doesn't care about extra grants on the refresh token), but **fresh consents via `slides-mcp-auth` only request `presentations.readonly`** going forward. If you want to lock the principle of least privilege end-to-end, re-run `slides-mcp-auth` with a fresh consent prompt to mint a token that has only the read scope.

## Why this is the right cut

The original North Star captured in `gsd-lite/PROJECT.md` was "user gives high-level intent, Claude realizes it as a visual presentation." After heavy iteration, the agent loop never closed cleanly on real brownfield decks. Every session ate 100k+ tokens on edge cases the API surface couldn't smooth over.

v2's vision is honest: Claude is excellent at *reading* slide content, *quoting* it, *summarizing* it, *finding* topics across decks. Let Claude do that, and let humans edit slides in the Slides UI where it works.

This unlocks the use case the user actually had: paste a deck URL, discuss it. Five tools, four detail modes, predictable token cost.
