# v2.7.0: place_image takes a picture from the agent's own disk

An agent could put an SVG it wrote or a public image URL on a slide, but not
a screenshot or a rendered chart sitting on its own disk. `place_image` now
takes that file as base64, and with mcp-piper the agent sends it as a file
pointer, so the bytes never pass through its context.

## New

- **`place_image(image_base64=...)`.** A third source beside `svg` and
  `image_url`; exactly one of the three. The type is read from the decoded
  bytes (PNG, JPEG or GIF); anything else, invalid base64, or more than 50 MB
  decoded is refused before any write. The image is hosted in the image
  bucket for Google to fetch and deleted straight after, the same way SVG is,
  so it needs the hosted server; over stdio the reply is error kind
  `hosting`. The receipt reports `placed.source == "base64"`. With mcp-piper,
  pass `"@file64:/abs/path.png"`.
- **Skill example: place, then move and resize.** The shipped skill shows
  placing a local picture and then moving and resizing it with a deck script,
  through `resize()` and `move()` on the receipt's `placed.object_ids`.

## Changed

- `render_thumbnail`'s description tells mcp-piper users to add `_save_to`
  to save the image to disk instead of reading it, and to ask for the smallest
  size when only the layout needs checking.
- The "no image hosting" errors name `image_base64` along with `svg`.

## Upgrade notes

- No new settings. A server that already has `SLIDES_MCP_IMAGE_BUCKET` set
  serves `image_base64` as it is.
- The server does not count pixels in an `image_base64` file. Google's own
  limit of 25 megapixels still applies, and its refusal comes back as error
  kind `google`.
