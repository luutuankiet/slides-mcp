# slides-mcp v0.3.0

Minor release — the "visual presentation" release. Closes the gap between
prompt-driven deck generation and Gamma-quality output through two phases of
work shipped together.

## TL;DR

An agent can now take a markdown doc or a natural-language intent and turn it
into a **coherent visual presentation** — not a text doc styled like slides.
Per-slide identity (Phase 1) + cross-slide theme coherence via an in-deck
meta-slide (Phase 2) means the agent commits once to a visual voice, then
materializes every slide in that voice without the human in the hot seat for
palette decisions.

## Why this release exists

Two visible gaps in v0.2.1:

1. **Monoculture output.** Prompt → deck generation produced 7/8 text_heavy_body
   slides (monochrome, no images, no structural variety). Gamma on the same
   README produced 16 slides with image anchors on every content slide, dark
   navy section openers, brand-consistent color story. The delta was real.
2. **No cross-slide language.** Even once Phase 1 landed per-slide variety,
   each slide picked its own palette independently. A 10-slide deck looked
   like 10 different decks — no viewer could tell they belong together.

Phase 1 closed the per-slide gap. Phase 2 closed the cross-slide gap. Both
ship here because they compose: per-slide identity + deck-level coherence =
the deck a consultant would actually present.

## Highlights

### Phase 1 — Visual-first primitives

| Change | What it does | Why it matters |
|---|---|---|
| `delete_slide(slide_id)` | One-call slide deletion | Collapses the 3-call `get_deck_outline` → `exec_batch_update(deleteObject)` → verify pattern |
| `create_image(deck_url, slide_id, at, url\|prompt)` | URL raster OR `[IMAGE: prompt]` placeholder | Placeholder-as-deliverable — stock/AI integrations no longer block visual output |
| `text_left_image_right` builder | Gamma's dominant content archetype | Kills the text-heavy monoculture — default content slide shape |
| `cover_with_hero` rewrite | Left/right side-hero + fullbleed modes with content-driven text colors | Section openers + deck covers with image anchors, per-slide palette control |
| `4col_numbered_flow` builder | 4-column numbered process layout | Structural variety without forcing an image slot |
| `normalize.py` scale readback fix | DSL readback now returns rendered dims instead of hard-coded 3.281 | Faithful round-trip was broken for any API-created shape |
| Autofit regression guard | Every fill `updateShapeProperties` carries explicit `autofit.autofitType: NONE` | Google Slides API change (post-2026-04) auto-applied non-NONE autofit during insertText, breaking subsequent batch requests |
| Skill rewrite — `rules/visual-presentation.md` | Renderer-not-brand contract, shapes-first, placeholder-as-deliverable, structural variety | The difference between a presentation and a text doc, spelled out for agents |

### Phase 2 — Cross-slide theme coherence via in-deck meta-slide

| Change | What it does | Why it matters |
|---|---|---|
| `set_theme_brief(deck_url, brief)` | Persist deck's visual DNA as a hidden `isSkipped` slide titled `__SLIDES_MCP_THEME_BRIEF__ — DO NOT DELETE` | Consumer-driven (agent writes from user intent), fork-safe (deck carries its own theme), server-stateless |
| `get_theme_brief(deck_url)` | Read the active brief, parse from body YAML | Every session start — one call to know the deck's voice |
| `update_theme_brief(deck_url, changes)` | Forward-only deep-merge patch | Mid-session amendments without touching existing slides |
| `extract_theme_brief(deck_url)` | Brownfield audit: propose a brief from an existing deck's dominant palette + shape topology | Decks that predate Phase 2 (or imports from elsewhere) can join the brief workflow |
| `create_slide(..., theme_brief=True)` | Server auto-resolves missing visual fields from the brief | Agent commits palette once, never repeats hex across calls |
| Resolution order in every builder | `per_slide_content > brief.palette.* > theme YAML > safety default` | Decision O preserved and extended — per-slide still wins for deliberate variation |
| Skill rewrite — `rules/theme-coherence.md` + `generate-from-intent.md` Step −1 | Greenfield/brownfield/amendment workflows + anti-patterns | Agents know when to commit the brief vs when to pass per-slide overrides |

## How the brief workflow looks

```mermaid
sequenceDiagram
    autonumber
    participant U as User
    participant A as Agent
    participant M as slides-mcp
    participant D as Deck<br/>(hidden meta-slide)

    U->>A: "Make a Q2 QBR deck from this README"
    A->>M: get_theme_brief(deck)
    M-->>A: status: absent

    A->>A: Translate intent → brief<br/>(navy + orange + editorial, sharp)
    A->>M: set_theme_brief(deck, brief)
    M->>D: append hidden slide<br/>title=__SLIDES_MCP_THEME_BRIEF__<br/>body=YAML brief<br/>isSkipped=true
    D-->>M: ok
    M-->>A: slide_id, action=created

    loop Each slide in the deck
        A->>M: create_slide(archetype, content)<br/>(no per-call palette)
        M->>D: fetch meta-slide<br/>parse YAML brief
        D-->>M: brief dict
        M->>M: resolve: per-call > brief > theme
        M->>D: batchUpdate: createSlide + shapes + text
        M-->>A: slide_id, brief_applied=true, thumbnail_url
        A->>M: render_thumbnail(slide_id)
        M-->>A: PNG ImageContent
        A->>A: verify visual
    end

    U->>A: "make the accent warmer"
    A->>M: update_theme_brief(deck, {palette: {accent: #D64518}})
    M->>D: deleteText + insertText on body box
    M-->>A: forward-only; existing slides unchanged
```

## Before / After

**v0.2.1 — intern round-2 on slides-mcp README (10 slides):**

- 5 archetypes ✅ (variety landed with Phase 1)
- **Each 3col_pill_cards slide picked its own palette** — Google-quad blue/green/yellow
  on one slide, vaporwave purple/pink/orange on the next. Cover used muted gray
  on light background with no palette echo.
- "Same deck" reading: no — three consecutive slides looked like three different decks.

**v0.3.0 — 3-slide coherence test with `set_theme_brief` + no per-call hex:**

- Cover (`cover_with_hero`): orange title (from `palette.accent`) + dark-gray subtitle
  (from `palette.text`).
- Narrative (`text_left_image_right`): orange accent bar under title + dark-gray body.
- 3-pillar (`3col_pill_cards`): orange title accent + pills in exact
  `palette.category_set` order (orange / navy / blue-gray).
- Zero per-call hex in any of the three content payloads.
- "Same deck" reading: yes — one visual voice across three archetypes.

## Configuration

No new env vars, no new config keys. The meta-slide is a zero-config feature —
call `set_theme_brief` and the deck carries its own theme.

Opt-out: `create_slide(theme_brief=False)` forces pre-v0.3.0 behavior (theme YAML
fallback only). Use for regression testing or deliberate bypass.

## Upgrade notes

**Backward compatibility.** All pre-v0.3.0 `create_slide` call sites work
unchanged. Brief absence degrades silently to theme YAML fallback. 124 pre-v0.3.0
unit tests pass without modification.

**Shape.** `create_slide` response gains one new key: `brief_applied: bool`.
Existing response keys unchanged.

**Hidden meta-slide in your deck.** After `set_theme_brief`, the deck gains one
new slide at the end. It is `isSkipped=True` — invisible in presentation mode,
visible in the editor. If accidentally deleted: Google Slides version history
restores it, and `create_slide` degrades gracefully to pre-v0.3.0 fallback
behavior until a new brief is committed.

**No registry / persistence changes.** theme_brief lives entirely in the deck.
No new files in `$XDG_CONFIG_HOME`. No new tables, no new caches.

## Known limits

- `palette.surface` is carried in the brief but not yet wired into any builder
  (reserved for future section-opener archetype, fullbleed overlay tint).
- `update_theme_brief` is **forward-only** — it patches the brief, future slides
  pick up the change, existing slides are untouched. Retroactive repaint
  (`restyle_slides`) is a named Phase 2.5 follow-up, not shipped here.
- `text_heavy_body` builder accepts the `brief` param for signature uniformity
  but doesn't consume it (deliberately minimal text archetype; brief applies via
  agent-side tone / image prompt hints instead of builder logic).
- The extraction heuristic (`extract_theme_brief`) picks dominant colors by
  area-weighted frequency; nearby-similar hexes aren't clustered yet. Agent
  reviews with user + tweaks before committing, which absorbs the precision
  gap.

## Hard truth

`theme_brief` solves coherence by convention, not by enforcement. The server
never rejects a per-call hex that conflicts with the brief — Decision O is
preserved (agent drives every call). An agent that ignores the brief and
passes fresh palette on every call gets the same v0.2.1 drift. The skill
documentation is the behavioral fix; `theme-coherence.md` + Step −1 of
`generate-from-intent.md` is the part of the release that changes what
agents actually do. Ship both the infra and the doc, or only half the
release happened.
